一、这个 App 解决什么问题

孩子做完作业或试卷后，错题散落在纸上。想整理成错题集通常要手抄一遍——费时、字丑、还容易抄错。

拍几张照片 → 自动切出每道错题 → 去掉孩子写过的笔迹，还原成干净的新题 → 挑出来排版打印。

核心价值是省掉手抄，并且能反复重做。

目标用户

角色用法
家长（主要用户）拍照、确认、挑题、打印
孩子做打印出来的练习卷

家里有两个孩子（二年级、四年级），所以必须支持多 Profile，两人的题目绝不能混。

二、多孩子 Profile（核心设计）

这是 v0.2 新增的一级设计，不是附加功能。

Profile（孩子）
├─ id
├─ 姓名 / 昵称
├─ 年级            二年级 / 四年级（影响 AI 出题难度）
├─ 头像（可选）
└─ 创建时间

规则

规则说明
题目必须归属某个 ProfileQuestion.profileId 是必填外键，不存在「无主」的题
全局只有一个「当前 Profile」顶部可随时切换，切换后整个 App（列表、打印、AI 提示词）都跟着变
不提供「全部孩子」视图避免一张卷子混进两个孩子的题。要合并打印，必须显式选择
拍照时先选孩子录入流程的第一步就是确认「这是谁的题」，默认当前 Profile
练习卷也归属 Profile生成后孩子姓名会印在卷子上（可关）

数据隔离做到存储层：所有查询都带 profileId 条件，而不是在界面层过滤。

这样漏掉过滤的代价是查询报错，而不是悄悄把两个孩子的题混在一起。

年级的作用

年级不只是个标签，它直接进入 AI 提示词：

  • 二年级：100 以内加减法、表内乘除、认识钟表/人民币、简单图形
  • 四年级：四则运算、运算定律、角度/平行垂直、三角形、条形统计图、小数

同一道题在不同年级的「变式题」难度不同。年级是变式题生成的关键参数。

三、核心流程

① 选孩子（默认当前 Profile）
        ↓
② 拍照 / 相册导入
        ↓
③ 自动处理（后台）
   ├─ 版面分析 → 自动切出 N 道题
   ├─ OCR 识别题干文字（本地或云端，按设置）
   ├─ ★ 批改：判断每道题做对还是做错（按设置开关）
   ├─ AI 重绘图形 / 公式（deepseek-flash 看图）
   └─ 自动分类：学科、知识点、难度
        ↓
④ 待确认列表  ★ 关键环节
   ├─ 逐题预览：原图 ↔ 重建结果 对照
   ├─ 显示批改结果：✓ 正确 / ✗ 错误 + 正确答案
   ├─ 可编辑：改文字、改对错、改正确答案、合并/拆分题目
   ├─ 逐题「通过」或「丢弃」
   └─ 【完成】按批改结果批量处理
        ↓
⑤ 确认后才真正入库（错题库）
        ↓
⑥ 错题列表：筛选 + 手动选择 / 多选 / 全选
   └─ 可在此生成变式题并加入选择
        ↓
⑦ 排版预览 → 一键打印（或导出 PDF）

④ 是这个设计的核心安全阀。自动处理一定有错，所以处理结果先进「待确认」，

只有用户点过确认的题才进错题库。这样错题库里永远是可信的。

三之二、拍照批改

批改和录入是同一条流程，不是两个功能。

理由：「错题」的定义就是做错的题。所以只要能判断对错，错题库就是自动筛出来的，

不需要家长自己判断哪道该收。反过来说，不批改时家长就是在手动完成这一步。

开关

批改在设置里控制，默认关：

设置默认说明
拍照后批改关打开后流程里多一步判断对错
用 AI 批改开关掉或没配 Key 时，自己点「做对了 / 做错了」
做对的题也入库关默认只留错题

两种批改方式

方式怎么工作需要
AI 批改把切出来的那道题（含孩子的手写答案）发给 deepseek-flash，让它判断对错并给出正确答案DeepSeek API Key
手动批改家长在确认页点「做对了 / 做错了」，再点一次撤销无，完全离线

为什么不做「答案比对」：题目和答案都是手写的，题型也五花八门（计算、

填空、应用题）。要比对得先有一份标准答案，而这里没有。视觉模型能同时看见题干

和孩子写的答案，直接判断——这是唯一可行的路子。

批改结果怎么用

  • 判错的题 → 进错题库（这是默认行为）
  • 判对的题 → 默认丢弃；打开「做对的题也入库」则入库并直接标成「已掌握」
  • 每道题都会存下正确答案，孩子重做时可以对照

出错怎么办

AI 会判错。所以：

  1. 批改结果只是建议，确认页每题都能改对错、改正确答案
  2. AI 的判断带 AI 标记，家长一眼能看出哪些需要复核
  3. 逐题记录失败原因，一道题失败不会让整批停摆

├─ 类型                 text | figure | formula

IntakeBatch（一次录入）★「待确认」的载体
├─ id, profileId, 创建时间

├─ id, batchId
├─ 原始裁剪图
├─ 自动处理结果（文字 / 图形 / 公式 / 建议分类）

Worksheet（练习卷）
├─ id, profileId, 名称

项选择

实现时的调整：drift → sqflite。

设计阶段选的是 drift，实际搭建时发现 drift 2.32 之后依赖的 sqlite3 3.x

会通过构建钩子在编译时从 GitHub 下载预编译的 SQLite 库，网络不通就整个

构建失败；而旧版本 drift 又与新版 build_runner 的 analyzer 要求冲突，无法

降级。sqflite 直接用 Android 系统自带的 SQLite，没有原生资源、不需要联网，

构建永远可复现。代价是失去编译期的查询检查，用一条纪律补回来：

任何读写题目的方法都必须接收 profileId。

OCR：双引擎，用户可选（已确认）

abstract class OcrEngine {
  String get id;
  Future<OcrOutcome> recognize(String imagePath);
}

class MlKitOcrEngine implements OcrEngine { ... }            // 本地，离线
class DeepSeekVisionOcrEngine implements OcrEngine { ... }   // 云端
引擎用什么优点缺点
本地Google ML Kit 端上文字识别离线、免费、照片不出设备、无按次费用APK 增大约 13MB；读不了手写体
云端DeepSeek 视觉模型（deepseek-flash）能读手写体、能理解版面、能把公式转 LaTeX照片要上传、按次收费、需联网

实现时改了选型：本地从 PaddleOCR 换成 Google ML Kit。

PaddleOCR 要自备并打包几十兆的检测+识别模型，还要自己串起检测、识别、

文本框合并，工程量很大。ML Kit 的中文识别是端上现成的，把模型打包进 APK

就是完全离线，代价只有 13MB。

而且题干本来就是印刷体——错题集要的是题目文字，不是孩子的手写答案，

那部分是批改模型的事。ML Kit 正好擅长印刷体。

设置里让用户选，并在界面上明确写出隐私代价：

云端 OCR 会把题目照片上传到 DeepSeek。题目里可能有孩子的姓名、学校、班级。

没配 API Key 时选云端会自动回退到本地——拍照录入是主流程，不该因为一个

可选配置而卡住。

AI：DeepSeek（已确认）

用官方 API（https://api.deepseek.com），两个用途：

用途模型说明
批改对错deepseek-flash多模态，看图判断做对做错，并给出正确答案
云端 OCRdeepseek-flash多模态，读手写体、理解版面、公式转 LaTeX

变式题生成deepseek-chat 或 deepseek-flash输入题干 + 年级 + 知识点

已核实：deepseek-flash 支持图片输入（[官方文档](https://api-docs.deepseek.com/zh-cn/guides/vision/)）。

这是「图形交给 LLM 生成」能成立的前提——模型看得见图，不是只靠文字猜。

七、题目清理怎么做（重点）

你提到的做法是：文字用文本重建，图形和公式用 LLM 生成，然后拼装成题目。

核实 DeepSeek 多模态能力后，这条路可行。下面是具体机制。

题干被建模成「元素序列」

[文字] "一个长方形的长是 8 厘米，宽是 5 厘米。"
[图形] （原题里那个长方形）
[文字] "求它的周长和面积。"

而不是一整块无法拆分的图片。每个元素独立处理，最后拼装回一道完整题目。

三类元素分别怎么处理

元素处理方式可靠性
文字OCR 识别 → 用户可编辑 → 重新排版高
公式OCR 出文字 → LLM 转 LaTeX → 排版渲染高（公式是纯文本，转换稳定）
图形裁剪原图 → 交给 deepseek-flash 重绘成 SVG中（见下）

图形重绘的机制

裁剪出的图形区域
     ↓  以 base64 传给 deepseek-flash
     ↓  提示词：识别图形内容，输出等价的标准 SVG（黑白线稿，适合打印）
     ↓
SVG 源码 → flutter_svg 渲染 → 嵌入题目

为什么选 SVG 而不是让 AI 生成图片：DeepSeek 的接口是对话补全，

输出的是文本。SVG 正好是「文本形式的图」，可以精确排版、无限缩放、打印清晰。

风险与应对（重要）

⚠️ AI 重绘的几何图可能与原题不完全一致——角度、标注、比例都可能偏。

应对：

  1. 默认不重绘，图形一律裁剪保留原图。AI 重绘是用户主动点的按钮。
  2. 强制对照：重绘后左右并排显示「原图 / AI 重绘」，用户看过才能选用。
  3. 打印时标记：使用 AI 重绘的题，在卷子角落标一个小记号，提示家长核对。
  4. 公式优先：公式走 LaTeX（可靠），只有图形才需要重绘——缩小风险面。

换句话说：AI 重绘是「可选增强」，不是默认路径。

默认路径（保留原图）永远是对的，只是可能带着笔迹。

成本（Token 机制）

已核实（[官方文档](https://api-docs.deepseek.com/zh-cn/guides/vision/)）：

  • 每张图片按尺寸换算 token，上限 1024 token
  • 图片会被自动缩放到约 1300×1300 等效像素
  • detail: low 会缩到 512×512，更快更省

推算：一道含图的题 ≈ 1 张图（≤1024 token）+ 题干文字（几百 token）。

一次录入 10 道题，大概几万 token 量级。具体单价请以官网为准。

省钱手段：

  • 图形裁剪后先压缩再上传（detail: low 对简单图形够用）
  • 只有含图形的题才调用视觉模型，纯文字题不调用
  • 用 DeepSeek 的上下文缓存（重复的前缀提示词不重复计费）

八、技术难点与应对

难点 1：自动切题不一定准 ⚠️ 高风险

试卷版面千变万化。全自动切分一定有错。

应对：自动切分只作预切分，进入待确认列表让用户调整（合并/拆分/重框）。

宁可多切几块让用户合并，也不要漏题。

难点 2：去掉手写笔迹 ⚠️ 中风险（已降级）

原本是最大风险，因为图像修复不可控。

已定方案：不做图像修复，走文本重建 + LLM 重绘。文字必然干净（是重新排版而不是修图）。

残留风险：图形重绘的准确性问题，见第七节。

难点 3：数学公式与图形 ⚠️ 中风险

应对：公式走 LaTeX；图形走「默认保留原图 + 可选 AI 重绘 + 强制对照」。

难点 4：变式题可能出错题 ⚠️ 中风险

LLM 生成的题可能条件矛盾、答案错误、难度不符。

应对：生成的题必须人工确认才入库；提供「重新生成」；界面标注「AI 生成，请核对」。

难点 5：两个孩子的数据不能混 ⚠️ 中风险

应对：profileId 进数据模型，存储层过滤而非界面层；不提供「全部」视图；

拍照流程第一步就确认归属。

难点 6：打印版式

不同题型（纯文字 / 含图 / 含公式）在 A4 上的排版不一致。

应对：统一「题目卡片」排版；图片按比例缩放限高；先做简单版式。
